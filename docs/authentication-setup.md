# Авторизация AxMed

## Реализованный сценарий

- Регистрация по email требует пароль: минимум 8 символов, хотя бы одна буква и одна цифра.
- Новый email подтверждается шестизначным одноразовым кодом.
- После подтверждения пользователь завершает onboarding.
- Повторный вход выполняется по email и паролю без кода.
- Активная сессия восстанавливается при запуске приложения.
- Выход отзывает серверную сессию и очищает защищённое хранилище телефона.
- Google и Apple credentials отправляются в API и проверяются на сервере.
- На экране входа есть «Забыли пароль?»: email → код → новый пароль → обычный вход.

## Восстановление пароля и ограничения входа

Восстановление доступно только для подтверждённых email-аккаунтов с паролем. Для неизвестного
адреса, неподтверждённого аккаунта и аккаунта только с Google/Apple возвращается одинаковый
ответ. Новый шестизначный случайный код действует 10 минут и отменяет все предыдущие коды
и разрешения на сброс. Повторная отправка — через 60 секунд, не более 5 запросов в час на email.
После 5 неверных кодов нужно запросить новый. Ограничения применяются и к неизвестным адресам.

Проверенный код обменивается на одноразовое разрешение смены пароля на 5 минут. Оно хранится
только в памяти экрана; в БД находятся HMAC кода и SHA-256 разрешения. Коды регистрации и
восстановления разделены. После смены пароля отзываются все прежние сессии, очищается пауза входа,
аннулируются остальные разрешения и отправляется уведомление. Автоматического входа нет.

Пять ошибок пароля за 15 минут приостанавливают вход на 5 минут. Счётчик привязан к нормализованному
email (в БД — HMAC адреса), сохраняется после перезапуска сервера и обновляется под блокировкой строки.
Пауза не продлевается дополнительными запросами; успешный вход и сброс пароля очищают счётчик.
Вход также ограничен 40 неуспешными запросами за 15 минут с IP, восстановление — отдельным лимитом
30 запросов за 15 минут с IP. Эти IP-лимиты хранятся в памяти процесса; при нескольких экземплярах
API нужен общий rate-limit store. Для reverse proxy следует отдельно настроить доверенные прокси.

Ответы 429 передают `Retry-After` и `error.retryAfterSeconds`; приложение показывает обратный отсчёт
и пересчитывает его при возвращении из фона. Новый dev build не нужен: изменения мобильной части — JS/TS.

Для восстановления обязателен SMTP. Настройки `AUTH_FIXED_VERIFICATION_CODE` и `AUTH_EXPOSE_DEV_CODE`
относятся только к регистрации: код восстановления всегда случайный и никогда не возвращается в API.
Письма отправляются асинхронно, чтобы время ответа SMTP не раскрывало наличие аккаунта. Ошибки
доставки фиксируются без email/кода; после сбоя или остановки процесса письмо можно запросить заново
по окончании cooldown. Если SMTP вообще не настроен, запрос отвечает `503 RECOVERY_UNAVAILABLE`.

Проверка в отдельной временной PostgreSQL-базе с локальным SMTP-приёмником (без внешней почты):

```powershell
npm run api:test:password-recovery
```

Команда создаёт собственную БД `axmed_auth_test_<uuid>` на локальном PostgreSQL и удаляет только
её после теста. Проверяются HTTP-сценарий, сохранение паузы в новом процессе, гонки запросов,
лимиты писем и кодов, истечение и повторное использование разрешений, отзыв access/refresh-сессий.

## Локальная разработка

PostgreSQL запускается через `docker-compose.yml`. Скопируйте оба шаблона окружения и не коммитьте реальные `.env`:

```powershell
Copy-Item .env.example .env
Copy-Item server/.env.example server/.env
npm run db:up
npm run api:dev
```

Для физического телефона `EXPO_PUBLIC_API_URL` должен содержать IP компьютера в локальной сети. `localhost` на телефоне указывает на сам телефон.

Без настроенного SMTP сервер в development-режиме возвращает код в поле `verificationCode`, и приложение показывает его подписью «Локальный код». Это поведение запрещено в production и автоматически дополнительно ограничено проверкой `NODE_ENV !== production`.

Для временной QA-проверки можно добавить в локальный `server/.env` `AUTH_FIXED_VERIFICATION_CODE=111111`. В production сервер всегда использует случайные коды.

## SMTP

Для реальной отправки писем заполните в `server/.env`:

```dotenv
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_SECURE=false
SMTP_USER=...
SMTP_PASSWORD=...
SMTP_FROM=AxMed <no-reply@example.com>
AUTH_EXPOSE_DEV_CODE=false
```

## Google OAuth

Мобильные Client ID задаются через `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` и `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID`. Эти идентификаторы публичные; Client secret в Expo добавлять нельзя.

API принимает разрешённые audience через `GOOGLE_CLIENT_IDS`. Он проверяет подпись Google ID token, issuer, audience и срок действия. Нативный Google Sign In требует development build и не работает внутри Expo Go.

Android package в приложении сейчас `com.axmed.mobile`. Для Android OAuth нужен клиент именно с этим package и SHA-1 сертификата development/production сборки.

## Apple Sign In

iOS bundle ID: `com.anonymous.pochka2new`, Team ID: `SAZ93YMRD7`. API использует bundle ID как `APPLE_CLIENT_ID` и проверяет Apple ID token по официальному JWKS, issuer, audience и сроку действия.

Имя Apple может прийти только при первом разрешении, поэтому API сохраняет его при создании аккаунта. Для production-hardening следующим шагом следует добавить server-issued nonce и обмен authorization code на Apple refresh token.

## Сессии

API возвращает короткий access JWT и случайный refresh-токен. На устройстве refresh-токен хранится в Expo SecureStore; в PostgreSQL хранится только его hash. При восстановлении сессии токен ротируется, а старый сразу отзывается.

Переменные `JWT_SECRET`, SMTP-пароль и строка подключения к production PostgreSQL являются серверными секретами и никогда не должны попадать в мобильный bundle.
