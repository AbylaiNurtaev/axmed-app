## Архитектура

`Четвёртый экран → DeviceGateway → ConnectionAdapter → AxmedHBand (Expo Module) → Veepoo SDK`

- Универсальный контракт: поиск, список устройств, подключение, отмена, отключение, подписка на состояние.
- SDK-специфичные классы находятся только в iOS-модуле. Весы смогут реализовать тот же контракт отдельным адаптером; регистрация не меняется.
- Сейчас зарегистрирован один адаптер `hband` для `fitness-band`. Несколько адаптеров одного типа потребуют явного выбора производителя; шлюз не выбирает случайный.
- SDK работает с одним активным браслетом. Команды последовательные. Добавлен foreground-only sync заряда и истории; фоновой синхронизации, автоматического переподключения и OTA нет.
- Bluetooth создаётся только после «Найти браслет». Поиск длится 12 секунд, подключение ограничено 45 секундами. Запрос разрешения можно отменить через экран; системное окно контролируется iOS.
- Физическое BLE-соединение — `verifying`, не `connected`. Готовность выставляется только после `BleVerifyPasswordSuccess`.
- ID устройства — UUID CoreBluetooth, не изменяемый SDK MAC/address. G72 или адрес пользователя не зашиты как найденное устройство.
- При уходе с экрана прекращаются поиск и незавершённое подключение; готовое соединение сохраняется. При уходе в фон во время чтения — отмена через отключение. При выгрузке bridge или выходе из аккаунта — отключение. Данные на API привязаны к пользователю из проверенного access token, а не к присланному userId.
- Expo Go, Android и web не имитируют Bluetooth: отображают сообщение о необходимости iOS dev-сборки.

## Первая облачная попытка и исправление

- [EAS build `aea61dfc-3e6e-4e84-9292-aecd8902badf`](https://expo.dev/accounts/axmed-project/projects/axmed/builds/aea61dfc-3e6e-4e84-9292-aecd8902badf): 11.09.2026, 14:09–14:13 UTC, `ERRORED` / `XCODE_BUILD_ERROR`. CocoaPods установились, Xcode начал Debug archive. App Store/TestFlight submission не запускался.
- Причина в Xcode log: `FMDB/src/fmdb/FMResultSet.m:3` импортирует `"unistd.h"`; Xcode выбрал `ReactNativeDependencies/Headers/folly/portability/Unistd.h`, после чего Objective-C компиляция упала на `namespace folly`.
- `plugins/with-fmdb-system-header.js` добавляет вызов `scripts/patch-fmdb-ios.cjs` в CocoaPods `post_install`, то есть после скачивания исходников и до компиляции. Исправление теперь меняет **только** `#import "unistd.h"` на `#import <unistd.h>` в двух сгенерированных файлах `ios/Pods/FMDB/src/fmdb/FMDatabase.m` и `FMResultSet.m`. Такой системный импорт используется в [upstream FMDB 2.7.12](https://github.com/ccgus/fmdb/blob/2.7.12/src/fmdb/FMResultSet.m), но сама зависимость остаётся **2.6.2**, как в vendor lockfile; ABI и SDK-бинарники не заменяются.
- Исправление идемпотентно, сохраняет права файла, проверяет оба файла до внесения изменений и ищет неохваченные quoted `unistd.h` импорты в остальных исходниках FMDB. Плагин подключён в `app.json`; используется и при EAS prebuild, и при локальном Expo prebuild/CocoaPods на Mac. Проверены 6 тестов, регистрация плагина в Expo и вставка в настоящий Podfile-шаблон установленного SDK 57. Дополнительно патч применён к временной копии реального FMDB 2.6.2 из пользовательского SDK: сравнены все 11 файлов, изменились только 2 импорта, исходная папка Downloads не изменена. **Третья EAS-сборка подтвердила применение патча к обоим файлам и успешную полную компиляцию.**
- Expo doctor в первой попытке: 20/21 проверок, предупреждение о небольших обновлениях `expo`, `expo-apple-authentication`, `expo-font`, `expo-linear-gradient`, `expo-secure-store`. Это не причина ошибки компиляции. Версии не обновлялись в ходе диагностики.
- Вторая попытка запущена с явного разрешения пользователя 11.09.2026 в 15:58 UTC: [EAS build `ce8c5337-8f32-4f7f-94b2-a6c9dd498d6e`](https://expo.dev/accounts/axmed-project/projects/axmed/builds/ce8c5337-8f32-4f7f-94b2-a6c9dd498d6e). Использованы `EXPO_NO_CAPABILITY_SYNC=1`, `--non-interactive --freeze-credentials` и существующие remote credentials. Capabilities/профили повторно не изменялись.
- Вторая попытка завершилась в 16:01 UTC, `ERRORED`. Лог CocoaPods подтвердил применение патча; Xcode показал конфликт уже в `FMDatabase.m:2`, который первоначальный патч не охватывал. По этой причине исправление расширено на оба импорта. Пользователь затем явно разрешил необходимые исправления и повторные сборки без отдельных запросов; третья попытка успешна, дальнейшие сборки не запускались.

## Комплект SDK

Использована предоставленная пользователем папка `iOS_Ble_SDK-master`, комплект demo, Veepoo **2.2.98.15**. Это не автоматически обновляемая latest-версия. SHA-256 бинарников закреплены в `modules/axmed-hband/vendor-manifest.json`.

Из demo импортированы VeepooBleSDK, ABParTool, DFUnits, GRDFUSDK, JLDialUnit, JL_BLEKit, ZipZap (около 31 МБ). Это согласованный комплект зависимостей; наличие DFU-библиотек не означает использование обновления прошивки. CocoaPods зависимости FMDB 2.6.2 и MJExtension 3.0.15.1 соответствуют vendor Podfile.lock. Нативная компиляция и линковка прошли в третьей EAS-сборке.

Бинарники лежат в `modules/axmed-hband/ios/Vendor`, игнорируются Git, но **включены в EAS-архив** через `.easignore`. Исходники сервера, `.env`, ключи подписи и дизайны не отправляются в архив. Проверьте условия коммерческого использования SDK у поставщика до распространения; исходный комплект не содержит подтверждения совместимости конкретного G72.

Другому разработчику нужно получить тот же комплект и выполнить один раз:

```powershell
powershell -NoProfile -File scripts/import-hband-sdk.ps1 -SdkPath 'C:\путь\к\iOS_Ble_SDK-master'
npm run devices:verify-sdk
npm run devices:test
npm run devices:test-build
npm run typecheck
```

Импорт сверяет хеши и не перезаписывает существующие файлы. Проверка SDK не запускает EAS Build.

## Тест на телефоне

- В G Band сначала использовать «Отключить», не «Забыть устройство». Не держать соединение в обоих приложениях одновременно (предупреждение SDK).
- Найти устройство в AxMed, выбрать свой браслет; подтвердить запрос на самом браслете, если появится.
- Проверить отказ в разрешении, выключенный Bluetooth, пустой поиск, таймаут, отмену, стрелку/свайп назад, повторное подключение и потерю связи.
- SDK автоматически проверяет стандартный пароль устройства и синхронизирует время в ходе handshake. Код не меняет пароль и не перебирает значения; ошибка проверки отображается пользователю.
- Успешный handshake подтверждает только подключение. Поддержку конкретных показателей, точность и протокол синхронизации проверяем отдельно.
