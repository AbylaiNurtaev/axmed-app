# Синхронизация браслета, MVP

11.09.2026. Пользователь подтвердил BLE-подключение G72 и первую синхронизацию: 32% заряда, 3520 шагов, 9 ч 13 мин сна, сохранение в аккаунте. Расширение v2 ниже пока требует проверки на его браслете; скриншот G Band сам по себе не доказывает получение данных AxMed.

## Реализация

`Veepoo → AxmedHBand → DeviceAdapter → SyncCoordinator → authenticated API → PostgreSQL`.

- После нового подключения запускается одна синхронизация, если есть активная сессия AxMed. Повтор — кнопкой на главной или в «Профиль → Подключённые устройства». После перезапуска приложения подключение выбирается заново; автоматического BLE reconnect пока нет.
- Команды строго последовательны: battery → base history → дополнительные oxygen / HRV / temperature (по возможностям прибора) → stored manual → activity. Это существующие методы [SDK поставщика](https://github.com/HBandSDK/iOS_Ble_SDK), сверенные с заголовками и Swift demo комплекта **2.2.98.15**. При `temperatureType == 5` отдельная команда температуры НЕ отправляется, она входит в base history. Другие SDK одновременно не обращаются к браслету.
- Таймауты: заряд 20 сек, base history 180, каждый дополнительный канал 120, manual 45, каждый activity query 20. Одна операция в native и JS. При отмене чтения, потере Bluetooth, уходе в фон, logout — отключение; устаревшие callbacks игнорируются по request ID и этапу. Таймаут прерывает весь read (без выдачи частичного batch как полного); SDK `.invalid` дополнительного канала даёт предупреждение, остальные этапы продолжаются.
- Старый native build/Expo Go не имитируют данные: показывается сообщение об установке сборки с sync.
- После завершения SDK-read из SDK DB извлекаются только данные выбранного устройства, за максимум 7 дней. SDK может хранить другие данные внутри своей БД, но API AxMed получает только разрешённые поля ниже. Не вызываются сброс браслета, стирание истории, OTA, изменение интервалов измерения или активные медицинские измерения.

| Поле | Источник | Семантика |
|---|---|---|
| Заряд | battery callback | Честные проценты либо 0–4 деления; деления не превращаются в проценты |
| Шаги | `stepValue` из original data | Количество за интервал; сегодня суммируются уникальные записи |
| Пульс | `heartValue`, затем `ecgs` / `ppgs`; manual `heartArray` | Ненулевой scalar либо среднее валидных элементов; массив помечается `aggregation: mean`, отдельные времена элементов не выдумываются |
| Сон | ordinary / accurate sleep DB methods | Длительность в минутах, начало/конец; связанные accurate-фрагменты объединяются, длительность берётся из последнего |
| Фазы сна | accurate durations; ordinary DEEP_HOUR / LIGHT_HOUR | Глубокий, лёгкий, REM, пробуждения в минутах; недоступные фазы — прочерк |
| Калории, расстояние | `veepooSDKGetStepData`, `deviceStature` | Суточные итоги kcal / km. Используется рост ИЗ БРАСЛЕТА, настройки не меняются; итог заменяется по стабильному ID дня, не добавляется повторно |
| SpO₂ | oxygen DB `OxygenValue`; manual `bloodOxygenArray` | %, последняя запись / среднее ручной записи |
| Давление | blood DB systolic/diastolic; manual h_bp/l_bp | mmHg, только целая пара одной записи и времени; названия полей не переставляются эвристически |
| Температура | temperature DB `value` | Документированные °C; не подменяется температурой поверхности кожи |
| HRV | HRV DB `hrvValue`; manual `hrvArray` | ms, без утверждения конкретной методики RMSSD/SDNN |
| Стресс, MET | original `stress` / `met`; manual stress.value | Значения поставщика, без собственной классификации «норма/повышено» |

Пустые данные — «—», ноль допустим только в полях, где он имеет смысл. Состояния «последние» и выбранный день не смешивают даты. Медицинского заключения и оценки «норма» нет; диапазоны валидации технические, не клинические нормы.

**Пока не импортируются:** глюкоза, ЭКГ, состав тела, компоненты крови, тренировки. На присланных скриншотах эти карточки пусты/нулевые, наличие карточки не подтверждает измерение. История, сохранённая только в G Band и уже отсутствующая в памяти G72, может быть недоступна SDK.

**Не подтверждены масштабы ручных `VPManualBodyTempModel.bodyTemp` и `VPManualMetModel.value`.** SDK документирует целочисленные поля без коэффициента перевода. Эти значения не конвертируются наугад и не отправляются как °C/MET; при их наличии выдаются warnings. Автоматические °C/MET читаются. Перед поддержкой этих двух ручных форматов нужен ответ поставщика/подтверждённая спецификация.

## Контракт и время

`DeviceSyncBatch`: `device { id, adapterId, kind, name }`, `readAt`, `timeZone`, `historyDays`, `skippedRecords`, необязательный `battery`, `samples[]`.

Запись: `sourceRecordId`, `metric`, `value`, `unit`, UTC `recordedAt`, необязательный `periodEnd`, SDK-local `localDate`, optional `aggregation` (`mean` / `dailyTotal`) и `origin` (`automatic` / `manual`). Batch v2 добавляет `syncVersion: 2` и `warnings`. Старый batch без этих полей остаётся совместимым, UI предлагает обновить dev client. ID интервала — стабильная локальная дата/время SDK + тип; sleep ID — локальное начало; manual ID — timestamp SDK. CoreBluetooth UUID используется как external device ID, MAC остаётся внутри native SDK.

SDK не передаёт отдельный часовой пояс истории. В MVP timestamps интерпретируются в текущем часовом поясе телефона; vendor SDK при handshake синхронизирует часы браслета. При поездках между поясами это ограничение необходимо учесть до аналитики. Исходная локальная дата сохраняется. Пульс и сон показывают дату/время измерения, отдельно от времени чтения.

## API и хранение

- `POST /api/devices/sync` — batch + `complete: true`, максимум 60 000 записей / 24 MB, авторизация и rate limit ДО разбора большого тела. Сервер валидирует единицы, диапазоны, даты и интервалы, отклоняет лишние поля.
- `GET /api/devices/readings` — последний синхронизированный прибор, до 60 000 недавних записей (окно 8 дней), только текущего пользователя. Старые записи в БД сохраняются, но полноценного API пагинации всей истории пока нет.
- Проверяются JWT algorithm/issuer/audience/subject и активный session ID в refresh_tokens. После logout тот же access token не получает доступ к показателям.
- Таблицы `health_devices` и `device_readings` создаются добавочной идемпотентной миграцией. Никакие прежние таблицы/аккаунты не удаляются.
- Полный batch пишется одной транзакцией; SQL разбит на порции по 250 внутри неё. UPSERT по device + metric + sourceRecordId исключает дубли; более старый sync не заменяет свежую запись.
- Чтение и сохранение — отдельные статусы. При ошибке API batch остаётся **в памяти текущей сессии**; «Повторить сохранение» не перечитывает SDK. Перезапуск приложения может потерять ещё не отправленный batch: повторная синхронизация читает историю с браслета. Полноценной долговременной offline-очереди пока нет.
- При смене пользователя сбрасываются JS snapshot/ожидающие операции, запросы отменяются и браслет отключается. Очередь SecureStore и ревизия сессии не дают позднему refresh восстановить токен после logout.
- Vendor DB хранится по адресу прибора; выборка выполняется только после законченного чтения этого устройства. Partitioning/удаление vendor-кэша по аккаунтам — отдельная задача перед production, SDK не предоставляет документированного per-account API в этом комплекте.
- Для production нужен HTTPS API, эксплуатационная политика хранения/удаления данных и проверка vendor data handling. Сейчас API локальный, как ранее настроенная авторизация.

## Проверки

```powershell
npm run typecheck
npm run api:typecheck
npm run devices:test
node --test tests/profile-logout.test.cjs
npm run api:test
npm run devices:test-api
npm run devices:verify-sdk
npm run devices:test-build
npm run devices:test-native # на macOS, также автоматически в EAS post-install
```

Integration test создаёт два временных UUID-аккаунта без отправки писем, проверяет 510 базовых и 12 008 расширенных записей, metadata/units, повтор, stale batch, изоляцию и отзыв сессии. Удаляет только созданные им аккаунты. `tests/device-readings-preview.cjs` — отдельная локальная UI-фикстура (не импортируется приложением): выбранный день, последние значения, пустые данные, ширины 320/390; в БД ничего не отправляет. Swift-тест нормализатора выполняется на macOS в EAS перед сборкой; он проверяет средние, нули, единицы, даты, сон и пары давления, но не заменяет физический BLE-тест.
